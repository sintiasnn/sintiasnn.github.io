From Route 53 to Hostinger: Moving an AWS App to a New Domain Without Moving DNS

Created on November 14, 2026

2026   ·   medium   ·   external-posts

It started with what sounded like a small task:

“We’re moving the app to the new domain.”

The app runs on ECS behind an Application Load Balancer, and from day one the ALB was pointed straight at a domain in Route 53. An alias record to the ALB, ACM certificate validation, all of it neatly in Terraform. The new domain, though, was bought on Hostinger.

Same app, same load balancer, new name. How hard could it be?

Harder than “just point the domain somewhere,” it turns out. Everything Route 53 used to handle quietly for us, the certificate validation and the records pointing at the ALB, now had to be set up again by hand on the Hostinger side. A new certificate, a handful of CNAMEs, and a few surprises along the way.

I could have moved the nameservers to Route 53 and kept working the way I was used to. But that would have been a whole project of its own. The domain was already set up and managed on Hostinger, so it stayed there.

Which meant the real job was this: rebuild, on Hostinger, everything Route 53 used to do for us. Without breaking the old domain while the new one came to life.

Every domain in this post uses the .example TLD, so swap in your own.

What you give up when you leave Route 53

Route 53 does a lot of quiet work that you only notice once it’s gone.

Alias records become plain CNAMEs. In Hostinger, you point a CNAME at the ALB’s DNS name. Never an A record to the ALB’s IPs, because those change without notice.

The alias health check disappears. evaluate_target_health mostly matters for failover. With one ALB and no failover, users get a 503 either way when every target is down. I let this one go.

ACM validation turns manual. Terraform can’t create the validation record anymore, so someone has to copy it into Hostinger’s DNS zone editor. And it has to stay there, because ACM reuses it for auto-renewal.

The records leave your IaC. terraform plan won’t notice if someone edits them. I compensated with a Terraform output that prints exactly what to create, plus a short list in the infra repo’s README. Not as good as state, but better than memory.

The apex can’t be a CNAME. DNS doesn’t allow it, since the apex already holds SOA, NS, MX, and TXT records. So the app lives on app.new.example, and the bare domain gets a redirect from Hostinger instead.

None of these are dealbreakers. But they’re worth knowing before you commit, not after.

The setup, briefly

The AWS side is well documented, so I’ll keep this short. Same ALB, same target group, same ECS service. Four changes:

  1. A second ACM certificate, validated by hand. Without Route 53, ACM can’t add its validation CNAME for you, so it goes into Hostinger manually (AWS docs). Our Terraform module always created that record in Route 53, so I added a manage_validation_record flag that skips it and prints the record as an output instead.
  2. The new cert on the existing HTTPS listener. The ALB picks the right certificate per hostname via SNI, so the old cert stays the default and the new one sits beside it.
  3. A host rule right next to the old one. Priority 101, directly after the old host’s 100, so the new domain behaves exactly like the old one. A separate rule also makes cleanup a one-resource change later.
  4. A CNAME in Hostinger pointing app at the ALB’s DNS name. Before creating it, I tested everything with curl --resolve, forcing the new hostname onto one of the ALB’s IPs.

For a while both domains had to work, which meant two things I almost missed. CORS on the API and the upload bucket had to allow both origins. And the frontend’s API URL is baked in at build time, so switching it meant a rebuild, not a config change.

That set the order: cert, listener, CORS, DNS, frontend. Every step only adds. The one rule I wouldn’t bend is CORS before DNS, because the moment the new domain resolves, its frontend starts calling the API from a new origin.

The things no guide warned me about

This is the part I actually wanted to write down, because I couldn’t find it anywhere else.

The DNS panel “helpfully” appended the domain. ACM gives you the full record name, something like _a1b2c3.app.new.example. Paste that into the Name field and Hostinger’s DNS panel, like many others, adds the domain again, so you end up with _a1b2c3.app.new.example.new.example. Validation just… never completes. Enter only _a1b2c3.app, then check it with dig before you start waiting.

Terraform gave up long before ACM did. aws_acm_certificate_validation waits 75 minutes by default. ACM waits up to 72 hours. So slow DNS propagation or a late copy-paste makes Terraform time out while the certificate is perfectly fine. Rerunning apply picks it back up. Better yet, split it into two applies: one to create the cert and print the records, one to validate and attach. The real risk is the opposite case. Leave a wrong record for 72 hours, and the cert has to be requested again.

A local apply rolled out a placeholder image. In CI, the image tag comes in as a variable. Locally, it defaulted to placeholder so plan wouldn’t complain. My apply for a certificate and a listener rule also quietly created a new task definition pointing at an image that didn’t exist. Lesson learned: no defaults on variables like that, and read the plan to the end. A task definition change in the middle of DNS work is a red flag.

An evening deploy woke the app while the database slept. This environment shuts down after hours. A scheduler stops RDS and scales ECS to zero. Terraform saw that desired_count didn’t match the code and “fixed” it. The app came up, the database didn’t, and the tasks restarted in a loop. Now desired_count sits in ignore_changes, and infra changes happen during working hours.

Don’t rush the cleanup

Once the new domain was stable, the tidy instinct was to delete everything old. I didn’t. The old domain still lives in bookmarks, sent emails, and third-party integrations, and its certificate costs nothing while it keeps auto-renewing through Route 53. When it’s time, switching the old rule to a 301 redirect is the gentler path.

The less technical part mattered just as much. Our ALB had no access logs, so I had no way to see who was still hitting the old domain. The only real safety net was telling people: the new domain, how long the old one stays up, and what to update. Bookmarks, env vars, webhooks, OAuth redirect URIs.

Why this was more than a DNS change

Here’s what I keep coming back to: the Terraform was the easy part. The hard part was everything Route 53 had been doing for us without anyone noticing. Alias records, certificate validation, renewals, all of it tracked in code. None of that moved with the domain. It all had to be rebuilt by hand, one CNAME at a time.

A domain move looks like a rename on paper. In practice, it’s a migration.

So if there’s one habit worth carrying into the next one, it’s this: before moving a domain, list what your current DNS setup quietly does for you. That list is your real migration plan.
