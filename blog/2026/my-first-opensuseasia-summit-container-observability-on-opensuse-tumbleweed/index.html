Why this talk

I work with Ubuntu-based infrastructure every day, and almost every “how to monitor Docker containers” tutorial assumes Ubuntu: apt, ufw, AppArmor. So I asked myself: what happens if I rebuild the same stack on openSUSE Tumbleweed? What breaks, what’s different, what’s easier?

Halfway through the session I noticed how many people had come, far more than I expected. I was nervous, but the questions afterwards made it worth it.

The stack in one picture

Three open-source tools, one pipeline:

  • cAdvisor reads each container’s cgroup statistics and serves them at /metrics on port 8080.
  • Prometheus scrapes that endpoint every 15 seconds and stores time series.
  • Grafana runs PromQL queries against Prometheus and draws the dashboards.

It’s a pull model over plain HTTP, so you can curl every step when debugging. I wanted per-container CPU, memory, network, and disk stored over time, because docker stats only shows the present, and a restarted container takes its numbers with it.

Building it on Tumbleweed

Docker comes straight from the openSUSE repositories, with no extra repo or GPG key:

sudo zypper refresh
sudo zypper install docker docker-compose
sudo systemctl enable --now docker
sudo usermod -aG docker $USER   # log out and in again

cAdvisor runs with read-only host mounts. I pin a version instead of using latest, and the image now lives on ghcr.io (older tutorials still point to gcr.io). I also don’t publish its port at all, because Prometheus reaches it by service name over the Compose network.

Prometheus needs only a short config:

global:
  scrape_interval: 15s
scrape_configs:
  - job_name: cadvisor
    static_configs:
      - targets: ["cadvisor:8080"]

Before building any dashboard, open the Prometheus Targets page and confirm the cadvisor job is UP.

For Grafana, add a Prometheus data source at http://prometheus:9090. Use the service name, not localhost, because Grafana runs inside a container. For a quick start, import community dashboard 14282.

Four queries that cover the basics

CPU, in cores:

sum by (name) (rate(container_cpu_usage_seconds_total{name!=""}[5m]))

Memory, in bytes:

sum by (name) (container_memory_working_set_bytes{name!=""})

Network receive, in bytes per second:

sum by (name) (rate(container_network_receive_bytes_total{name!=""}[5m]))

Disk writes, in bytes per second:

sum by (name) (rate(container_fs_writes_bytes_total{name!=""}[5m]))

Two habits worth keeping. Use rate() over 5 minutes, because these are counters. And filter name!=”” so host-level cgroups don’t clutter your view.

For memory alerts, use working set, not raw usage. container_memory_usage_bytes includes page cache the kernel can reclaim, so it often looks scarier than reality. Working set is much closer to what leads to an OOM kill.

In my demo, a container called cpu-hog runs an endless loop but is started with — cpus 0.5. The dashboard shows its CPU line sitting flat at exactly 0.5 cores: the cgroup limit at work, read by cAdvisor straight from the kernel.

What changed compared to Ubuntu

  • Packages: apt on Ubuntu, zypper on openSUSE.
  • Docker source: Docker’s own apt repo on Ubuntu, the openSUSE OSS repo on Tumbleweed.
  • Firewall: ufw on Ubuntu, firewalld on openSUSE.
  • Security module: AppArmor on Ubuntu, SELinux (enforcing on new installs) on Tumbleweed.
  • Root filesystem: ext4 on Ubuntu, Btrfs with Snapper snapshots on Tumbleweed.

The monitoring tools don’t care about the distro. What changes is the plumbing around them. Three things to check before you trust your dashboard:

1. SELinux labels. A bind-mounted config can fail with “permission denied”. Add :Z to the volume, confirm with ausearch -m avc, and keep SELinux enforcing.

2. Docker’s storage backend. On my Tumbleweed, Docker uses the containerd image store, so cAdvisor needs the containerd socket, which lives in /run/docker/containerd. My first run collected metrics but no container names, until I mounted that socket.

3. Published ports. Docker writes its own firewall rules, so a published port can be reachable even when firewalld doesn’t list it. I saw this myself: Grafana on port 3000 was open to the internet while firewalld only allowed ssh. Bind Prometheus to 127.0.0.1, don’t publish cAdvisor, and change Grafana’s default admin password first.

One caveat: I tested all this on a minimal Tumbleweed install on a cloud server with a public IP, not on a laptop. A minimal install has no sudo or SELinux tools by default, and on a public server, port exposure matters much more than on a VM behind NAT.

Takeaways

  • The stack stays the same; openSUSE changes the plumbing.
  • Check SELinux labels, the storage backend, and published ports before trusting your numbers.
  • Start from dashboard 14282, then add your own PromQL panels.
  • If you’ve only used Ubuntu like me, try Tumbleweed. It was a lot less scary than I expected.

If you want to scale this beyond one host, Geraldhi Aditya Putra Mahayadnya’s summit talk on distributed monitoring with Prometheus and Thanos is the natural next step. Podman is my next experiment on Tumbleweed.
