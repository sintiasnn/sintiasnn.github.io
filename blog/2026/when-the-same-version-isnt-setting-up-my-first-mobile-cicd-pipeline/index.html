When “The Same Version” Isn’t: Setting Up My First Mobile CI/CD Pipeline

Created on September 16, 2026

2026   ·   medium   ·   external-posts

A cross-platform version-pinning bug that only shows up once your Android and iOS release jobs are both live — and the fix that made them agree on the same Flutter revision.

The Hook

One day, my pipeline threw this:

A release with version 1.0.0+107 already exists but was built using a different Flutter revision.
Existing release built with: 3.41.6 (abc1234)
Current release built with: 3.47.0 (def5678)

This showed up while I was setting up a mobile CI/CD pipeline for the very first time — and touching an iOS pipeline for the first time too. Two jobs, two platforms, both nominally building the “same” version. Turns out they weren’t.

This post is a record of the debugging process — not a plan I had going in, but something I genuinely found one failure at a time.

Why This Happens

The core insight I only got after a fair amount of debugging: a code-push tool (Shorebird, in this case) isn’t just something you invoke inside your existing CI toolchain. It vendors its own Flutter checkout, completely separate from whatever Flutter is baked into your image or runner.

So if your job runs inside an image with Flutter 3.41.6, that has zero effect on what Shorebird actually builds with — unless you explicitly tell it which version to use. Left unpinned, it silently defaults to whatever the latest stable Flutter it has mirrored is.

There’s a subtler constraint on top of that: the tool enforces that every platform under one release version must be built from the exact same Flutter revision. This constraint only becomes visible once two platforms (Android and iOS) both attempt a release for the same version — testing a single platform in isolation gives you false confidence that everything’s fine.

Timeline (As Discovered, Not As Planned)

This is my favorite part to tell, because none of it was anticipated up front — it was all found the hard way.

1. An invisible prerequisite. The very first job failed before any of this, because the CI image had no Node at all — so it wasn’t just the code-push tool that couldn’t run, supporting scripts (like the build-number generator) couldn’t either. Not the real fix, but nothing else moves without it.

2. Iteration 1 — looked right, was only half right. The Android job failed at the Gradle-plugin-apply step. Turned out the newer Flutter version (which the tool picked up unpinned) required a higher minimum Gradle version than what the project had pinned. First fix: read the Flutter version off the job’s own image and pass it explicitly to the code-push tool. Android-only.

3. Iteration 2 — ~19 hours later, and only then did it become clear why iteration 1 wasn’t enough. The iOS job failed too, but not on Gradle — on the cross-platform revision-lock check above. Why didn’t “read the version from the image” carry over to iOS? Because the iOS runner is bare-metal macOS, not a container — there’s no image tag to read a version from. Only at this point did it become clear the fix had to be platform-agnostic: one pinned file both jobs read, not “derive it from whatever environment this job happens to be in.”

Root Cause, In Short

Two independent facts colliding:

(a) The code-push tool’s Flutter is out-of-band from your CI image’s Flutter, and defaults to “latest stable” when unpinned.

(b) The tool enforces Flutter-revision consistency across platforms for a given release version — something a single-platform pipeline will never catch.

The Fix

A single version-pin file at the repo root, read by both platform jobs through a shared CI template, validated against a strict format check that hard-fails the job rather than silently proceeding with an empty string.

# flutter-version.json at repo root: { "flutter": "3.41.6" }
jobs:
  release-android:
    steps:
      - id: pin
        run: |
          FLUTTER_VERSION=$(jq -r .flutter flutter-version.json)
          [[ "$FLUTTER_VERSION" =~ ^[0-9]+\.[0-9]+\.[0-9]+$ ]] || { echo "bad version"; exit 1; }
          echo "flutter_version=$FLUTTER_VERSION" >> "$GITHUB_OUTPUT"
      - run: shorebird release android --flutter-version=$
  release-ios:
    steps:
      - id: pin
        run: |
          FLUTTER_VERSION=$(jq -r .flutter flutter-version.json)
          [[ "$FLUTTER_VERSION" =~ ^[0-9]+\.[0-9]+\.[0-9]+$ ]] || { echo "bad version"; exit 1; }
          echo "flutter_version=$FLUTTER_VERSION" >> "$GITHUB_OUTPUT"
      - run: shorebird release ios --flutter-version=$

One thing that’s easy to get wrong: the patch job (as opposed to release) deliberately does not use this pin.

# release jobs: pin --flutter-version explicitly (source of truth = repo file)
# patch jobs: this flag is DELIBERATELY omitted — the tool automatically
# inherits the revision the release being patched was built with.
# If a patch job followed the repo's current pin instead, a patch could
# silently target a different Flutter revision than the release it's
# patching was actually built with.

Bonus Root Cause: The Moving Gradle Floor

Flutter’s minimum required Gradle version shifts between minor releases. So a code-push-tool-side Flutter bump that looks completely harmless can break a project still pinned to an older Gradle wrapper — with zero lines of app code changed. This class of bug is confusing because the error looks like a Gradle problem, when the actual root cause is an unpinned Flutter version.

Side Story: A Build Number That Couldn’t Be Trusted From Any Single Source

The obvious first idea was to just read it from pubspec.yaml or the platform's official distribution CLI. Neither held up:

  • The official CLI used for Android distribution has no command to list releases that have already shipped — it can only push, not query.
  • pubspec.yaml itself, once checked, had drifted from what was actually live in the stores — not a hypothesis, a confirmed fact.

The fix: query the distribution platform’s REST API directly, page through every release that’s ever existed, filter out anything expired, take the highest surviving build number, and increment it.

function nextBuildNumber(distributionApi, fallbackFromManifest):
    releases = paginateAll(distributionApi.listReleases())
    nonExpired = releases.filter(r => !r.expired)
    if nonExpired.isEmpty():
        return fallbackFromManifest + 1   # brand-new app only
    highest = max(nonExpired, by: r => r.buildNumber)
    return highest.buildNumber + 1

This logic itself only became correct on the fourth attempt — an early version mistakenly used the CI pipeline’s own run number as the build number (jumping by thousands), and a later version forgot to exclude expired builds from the “highest” calculation.

Release vs. Patch: Who Decides?

Turns out it’s not automatic — and that’s a deliberate choice, not a tooling limitation. The code-push tool has a technical guard (it refuses to patch if the diff touches assets, native code, or dependencies), but the final call on “should this ship as a patch or a full release” stays a human judgment, because “is this diff Dart-only” isn’t something you want a heuristic guessing at — guessing wrong means shipping mismatched assets to production.

patch result:
  if diff touches: assets/, native code, dependencies
    => REFUSE ("ship a full release instead")
  else
    => proceed (Dart-only patch)
  # a flag exists to force past this guard — treat it as a documented
  # footgun, not a normal escape hatch

Lessons

  • A deploy tool that vendors its own toolchain has a second version-resolution system you must pin explicitly — don’t assume “my CI image already pins the version” covers it.
  • A constraint that only surfaces when two independent pipelines converge (here: two platforms, two runner types) won’t show up until you actually run both — testing a single job gives false confidence.
  • “Derive the fix from the local environment” (an image tag) is a trap when your job types don’t share an environment (container vs. bare-metal runner) — prefer a single file both read instead.
  • When a vendor CLI has no introspection/list command, you’ll end up reverse-engineering its REST API — budget time for it, and expect it to take a few correctness passes (pagination, excluding expired entries, etc.), not to work on the first try.
